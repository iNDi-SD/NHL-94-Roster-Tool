NHL '94 Roster Tool How the web app reads, edits, and writes player and team data inside a Genesis ROM binary.

A Sega Genesis ROM is a binary file. All player and team data lives at fixed memory addresses inside it. This tool reads those raw bytes out to an XLSX spreadsheet and writes modified data back in. No game engine is involved; it's byte manipulation in the browser using SheetJS (xlsx-latest CDN) for spreadsheet I/O.

All logic lives in the inline <script> block at the bottom of web/index.html, starting around line 340. Function references appear throughout this guide as chips with exact line numbers in index.html.

ROM Structure: The Pointer Table

At byte offset 782 is a table of pointers, one per team. Each pointer is 4 bytes and holds the absolute file offset of that team's data block. Every team lookup starts here.

readtmPtrs(d)L:349 readu32(d, o)L:346 writewriteU32(b, p, v)L:380

tmPtrs() calls u32() at 782 + (i × 4) for each team index, returning an array of absolute byte offsets. After import, writeU32() patches these pointers to their new positions before writing the checksum.

Big-endian: The Genesis CPU (Motorola 68000) stores integers most-significant byte first. u32 and u16 reconstruct values using manual bit shifts: (d[o] * 0x1000000) + (d[o+1] << 16) + ...

Team ratings: bytes 76–78

Three bytes pack six values using nibbles. Byte 76 holds Offense (high nibble) and Defense (low nibble). Byte 77 holds PK and PP. Byte 78 holds Home and Road. Export reads them with >> 4 and & 0xF; import packs them back with (off << 4) | def.

Goalie count: bytes 80–81

readGoalieCount() converts these two bytes to a hex string and counts leading non-zero hex digits. goalieBytes(n) reverses it: 1 goalie → [0x10, 0x00], 2 → [0x11, 0x00], 3 → [0x11, 0x10], 4 → [0x11, 0x11].

Player count: byte 79

The high nibble of byte 79 is nF (forward count); the low nibble is nD (defense count). Goalie count comes from bytes 80–81. These three values determine player position during both export and import.

Name length field (nml)

The nml u16 counts itself. A 13-character name like "Wayne Gretzky" has nml = 16: 13 chars + 1 padding byte (to reach even alignment) + 2 for the length field itself. A 12-char even-length name has nml = 14: 12 chars + 2. Padding is only appended when the character count is odd; the Genesis requires word-aligned data.

On import, importPlayers() computes nml = name.length % 2 === 0 ? name.length + 2 : name.length + 3. The XLSX stores First and Last separately; the ROM stores them as "First Last" with a space. The combined name must be ≤ 20 characters.

Jersey number

One byte, stored as its hex value directly. Jersey #17 is stored as 0x17. The XLSX column JNo uses one- or two-character hex strings: 11, 17, 0A.

Position detection

There is no position byte in the record. Position is inferred by counting: the first nG players are goalies, the next nF are forwards, the rest are defense. nG comes from bytes 80–81 via readGoalieCount(); nF comes from (data[ptr+79] >> 4) & 0xF.

readTeamName() reads all four strings sequentially from ptr + tmOff. parseNameSections() walks the four strings to measure their total byte length, which is needed to find where the last team's block ends (since there's no next pointer to bound it). buildNameSection() encodes a string back to this format for import.

Team names are only written during import when the XLSX contains the optional Team City, Team Name, and Arena columns. If those columns are absent, only ratings are patched and the existing name strings are left untouched.

Team overall ratings (0–99) live in a flat array completely separate from the team blocks. One byte per team, in the same order as the pointer table.

On export, each byte is decoded as (byte >> 4) & 0xF (high) and byte & 0xF (low), producing the 14-element att[] array. On import, buildAttrNibbles() assembles the 14 nibble values into a 14-character hex string, then pairs them with parseInt(attr.slice(b*2, b*2+2), 16) for each byte.

The double-width fields (Wgt and Hnd, 0–15) use parseInt(v).toString(16) to produce a single hex digit. All other attributes (0–6) are stored as their decimal value directly as a hex character.

Team Count Detection

ROMs come in 30-team and 32-team variants. The tool auto-detects which by reading the pointer table heuristically, without a file-size check.

readdetectTeamCount(data)L:640

detectTeamCount() reads 34 potential pointers starting at offset 782 and counts how many consecutive ones satisfy two conditions: each pointer is greater than the previous (ascending), and each pointer is within the file's bounds. It maps the count to a ROM type:

Valid pointer runDetected type
≥ 32 consecutive valid pointers32-team ROM
≥ 30 consecutive valid pointers30-team ROM
fewer than 30null — unrecognized

If the detected count conflicts with the toggle, the operation is blocked with an error. If detection returns null, the operation proceeds using the toggle value as-is.

Player Block Space Calculation

importPlayers() cannot simply append data. Each team block must fit within space defined by consecutive pointer offsets, because other game data lives immediately after the last block. The tool redistributes the existing total player-area space evenly across teams.

importimportPlayers() — space calcL:453

The algorithm:

  1. Read the existing tmOff for every team. The player area for each team is tmOff − 146 bytes.
  2. Sum all player areas to get totalSpace. Compute baseEven as the largest even number ≤ totalSpace / nTeams.
  3. Compute leftover bytes: extra = totalSpace − baseEven × nTeams. The last extra / 2 teams get baseEven + 2 bytes; the rest get baseEven.
  4. Before writing, verify that each team's actual player bytes + 2 (the 0x00 0x02 sentinel) fit in the allocated space. If not, an error is thrown.
  5. Within each block, bytes between the 146-byte header and plOff are filled with 0xFF. Player records are written from plOff. The existing name string bytes are copied verbatim to tmOff.

The pre/post data around the entire team block area is preserved unchanged. The pointer table at offset 782 is patched to reflect the new block positions before the checksum is recalculated.

32-team ROMs use BLOCK_AREA_END[32] = 2030418 as a hard boundary for the last team's block. 30-team ROMs derive the boundary by measuring the last team's name strings with parseNameSections().

Checksum

Genesis ROMs include a 16-bit checksum at bytes 0x18E–0x18F. Both importTeams() and importPlayers() recalculate it after writing. The algorithm sums every big-endian u16 starting at 0x200 and wraps at 16 bits:

writeimportTeams() — checksumL:540 writeimportPlayers() — checksumL:492

The loop: for (i = 0x200; i+1 < rom.length; i += 2) ck = (ck + (rom[i] << 8) + rom[i+1]) & 0xFFFF. The result is split into two bytes and written to rom[0x18E] and rom[0x18F]. Without a valid checksum, many emulators and flashcarts refuse to boot the ROM.
